# Inspection: Slow Live Stream Video Start

## Summary

After full inspection of the backend, **five interacting factors** likely cause the "video takes longer to start" symptom. No single silver bullet — it's a combination of cloudscraper overhead, retry amplification, circuit breaker blocking, negative cache poisoning, and low connection pool limits.

---

## Root Cause Analysis

### 1. Cloudscraper Anti-Bot Challenge Overhead (HIGH — primary suspect)

**File:** `services/kick_api_service.py:59`

```python
s = cloudscraper.create_scraper()
```

`cloudscraper` (v1.2.71 — last release Apr 2023, effectively abandoned per `requirements.txt`) solves Cloudflare challenges by executing JavaScript locally before making the real request. This adds **significant latency** to every HTTP call that triggers a challenge:

- First request to a fresh Kick domain/path may need to solve a JS challenge (~1-3s extra)
- The library is unmaintained and may fail against newer Cloudflare challenges, falling back to slower strategies
- Cloudflare challenge tokens are short-lived; if a thread's session doesn't get enough traffic, the token expires and the next request must re-solve

**Impact on video start:** The `/streams/play/{slug}` endpoint calls `client.get_channel_data()` which goes through cloudscraper. On a cold session or when Cloudflare rotates challenges, this adds seconds before the playback_url is even returned to the frontend.

### 2. Retry Strategy Amplifies Latency on Upstream Failures (MEDIUM-HIGH)

**File:** `services/kick_api_service.py:38-43`

```python
_RETRY_STRATEGY = Retry(
    total=2,
    backoff_factor=0.3,
    status_forcelist=[502, 503, 504],
    allowed_methods=["GET"],
)
```

With `total=2` and `backoff_factor=0.3`, a single failing request retries up to 2 times with delays of 0.3s and 0.6s. Combined with cloudscraper overhead, a single `get_channel_data()` call that encounters a 502/503/504 can take:

- Attempt 1: ~3s (cloudscraper + timeout)
- Wait: 0.3s
- Attempt 2: ~3s
- Wait: 0.6s
- Attempt 3: ~3s
- **Total: ~9.9s** for one channel lookup

The `get_channel_data` timeout is 8s, but the connect timeout is only 3s (`timeout=(3, timeout)` at line 71), so each attempt can take up to 11s before the retry kicks in. This blows well past the frontend's 10s `API_TIMEOUT_MS`.

### 3. Circuit Breaker Blocks ALL Endpoints After Failures (MEDIUM-HIGH)

**File:** `services/circuit_breaker.py`, `config.py:68-69`

```
CIRCUIT_BREAKER_FAILURE_THRESHOLD = 5
CIRCUIT_BREAKER_RECOVERY_SECONDS = 30
```

**Single shared instance** across all endpoints (created in `app.py:139`). When ANY 5 upstream calls fail (e.g., viewer count polls, search queries, featured fetches), the breaker opens and **every** subsequent request — including `/streams/play/{slug}` — gets an instant 503:

```python
# _common.py:50-51
if circuit_breaker is not None and not circuit_breaker.allow_request():
    raise ApiError("Service temporarily unavailable — upstream failures detected.", 503)
```

The breaker stays open for 30s. During that window, every video start attempt fails immediately. If the user retries, they still get 503 for up to 30 seconds. This is especially bad because:

- Non-critical endpoint failures (viewer counts, search) trigger the breaker
- The breaker has no per-endpoint granularity
- 30s is a long wait for a video start

### 4. Negative Cache from 429 Poisons Live Stream Lookup (MEDIUM)

**File:** `api/routes/channel.py:129-132`, `config.py:64`

```python
NEGATIVE_CACHE_DURATION_SECONDS: int = Field(10, ge=1)
```

When Kick rate-limits a channel request (429), the error response is cached for 10 seconds:

```python
if exc.status_code in (404, 429):
    err_payload = {"status": "error", "message": exc.message, "data": {}}
    cache.set(stale_key, (err_payload, exc.status_code), timeout=Config.NEGATIVE_CACHE_DURATION_SECONDS)
    cache.set(fresh_key, True, timeout=Config.NEGATIVE_CACHE_DURATION_SECONDS)
```

During those 10 seconds, every `/streams/play/{slug}` request returns the cached 429 error immediately — no retry, no fallback, no stale-while-revalidate. The user sees "Rate limited by upstream service" and the video doesn't start.

This is particularly problematic because:
- The `fresh_key` is also set, which prevents stale-while-revalidate from even attempting a background refresh
- 429 from one channel's request can coincide with a user trying to watch that channel
- The 10s window feels like a hang when the user is waiting for video

### 5. Thread-Local Session Connection Pool Limits (LOW-MEDIUM)

**File:** `services/kick_api_service.py:64-65`

```python
adapter._pool_connections = 5
adapter._pool_maxsize = 10
```

Each thread-local session gets 5 pool connections and a max of 10. Under load with `asyncio.to_thread()` using a shared thread pool, multiple threads each create their own sessions with their own connection pools. This means:

- More total connections to Kick than intended (N threads × 5-10 connections)
- But each individual pool is small (5), so within a thread, connection reuse may be suboptimal if the thread handles requests to multiple Kick URL patterns
- On the Pi (single worker, limited resources), this fragmentation wastes file descriptors

## How The Factors Combine (The Full Failure Scenario)

1. User clicks a live channel → frontend calls `/streams/play/{slug}`
2. Backend's `get_channel_data()` goes through cloudscraper → Cloudflare challenge adds 1-3s
3. If Kick returns 502/503, retry strategy adds up to ~10s total
4. If concurrent viewer-count polls also fail, circuit breaker opens (5 failures) → ALL requests get 503 for 30s
5. If Kick returns 429, negative cache poisons the channel for 10s — no retry possible
6. Frontend's 10s timeout fires → user sees "Request timed out"

Even in the happy path (no failures), cloudscraper's JS challenge solving adds consistent latency that makes the video start feel slow compared to a direct Kick request.

---

## Recommended Fixes (Priority Order)

| # | Fix | Impact | Effort |
|---|-----|--------|--------|
| 1 | **Replace cloudscraper with a maintained alternative** (e.g., `curl_cffi` with browser impersonation, or direct requests with proper headers + cookie jar) | Eliminates 1-3s JS challenge overhead per request | Medium |
| 2 | **Reduce retry count or scope retries**: `total=1` instead of `2`, or remove 502 from `status_forcelist` (Kick often returns transient 502s that self-resolve on next request) | Cuts worst-case from ~10s to ~5s per call | Low |
| 3 | **Per-endpoint circuit breaker or higher threshold**: Separate breaker for critical paths (play, go) vs non-critical (viewers, search), or raise threshold to 10+ | Prevents non-critical failures from blocking video start | Medium |
| 4 | **Don't negative-cache 429 on the play endpoint**: Only cache 429 errors for 2-3s, or skip caching 429 entirely for `/streams/play` so the next request gets a fresh attempt | Eliminates the 10s "dead zone" after rate limiting | Low |
| 5 | **Increase per-thread pool sizes or share connection pools** across thread-local sessions | Marginal latency improvement on connection reuse | Low |

---

## Quick Win Combination

The highest-impact, lowest-effort changes would be:

1. Reduce retry total from 2 → 1 (cuts worst-case latency in half)
2. Raise `CIRCUIT_BREAKER_FAILURE_THRESHOLD` from 5 → 10 (fewer false-open events)
3. Reduce `NEGATIVE_CACHE_DURATION_SECONDS` for 429 specifically (or skip 429 caching for play endpoint)
4. Consider `curl_cffi` as a cloudscraper replacement (larger effort but biggest win)
